#+TITLE: Should the planner be split back into a separate package?
#+AUTHOR: Claude (Fable 5)
#+DATE: 2026-07-30
#+STARTUP: overview

Question under analysis: separate =planning/= back into the standalone
=org-scribe-planner= package (as before v0.5.0), making the planner "an
optional module we can add to a project." Evidence: the current
=development= branch, the original standalone repo
(https://codeberg.org/jcastp/org-scribe-planner, cloned and compared), and
the findings in [[file:fable-plan.org][fable-plan.org]] / [[file:bugs-fable.org][bugs-fable.org]].

* TL;DR — Recommendation

*Do not split the packages again.* The costs that motivated the v0.5.0 merge
are all still present and one of them is now worse (the standalone repo has
drifted 1,000+ lines behind and is missing five months of bug fixes). What
you actually want — "an optional module we can add *to a project*" — is a
*per-project* opt-in, not a *packaging* split, and the current architecture
is already 90% of the way there: the planner costs nothing and does nothing
until explicitly invoked. Close the last 10% with a small per-project gate
(design in §6), archive the standalone repo, and revisit separation only
after the slimming work in fable-plan.org §8, if ever.

* 1. History: what the split looked like, and why the merge happened

The standalone repo tells its own story:

- Last commit *2026-02-19* — stale for over five months while the bundled
  copy kept evolving.
- =org-scribe-planner.el= there is *1,912 lines* vs. *2,822* bundled; a diff
  between the two shows *~1,058 changed lines*. The bundled version has
  since gained the whole integration section (lines 2350–2822), agenda
  sync, session notes, the =SYNC_DATE=/=SYNC_WORDS= daily-tracking model,
  and the DST/date fixes from the 2026-07-29 bug review (bugs-fable.org
  H1). None of that exists in the standalone repo.
- Its recent history includes a commit *"removed circular dependency"* —
  direct evidence that the two-package arrangement produced exactly the
  coupling pathology you'd expect: each side wanting to know about the
  other.
- The fossil on this side: =integration/org-scribe-planner-integration.el=,
  now an empty shim, is what remains of the bridge file that the two-package
  era required. The bridge problem (see §4) does not go away by splitting
  again; it comes back.

So the historical experiment already ran once, and its residue — a stale
repo, a circular-dependency fix, a dead shim — is the data.

* 2. How coupled are they today? (Measured, both directions)

** Planner → org-scribe (the heavier direction)
The planner references exactly five org-scribe functions
(=planning/org-scribe-planner.el:2356-2360=): =org-scribe-project-root=,
=org-scribe-project-structure=, =org-scribe-ews-org-count-words=, and the
two project-creation commands. Every use is confined to the "org-scribe
Integration" section (lines 2350–end) and wired inside a single
=(with-eval-after-load 'org-scribe ...)= block (line 2712) plus a
=(when (require 'hydra nil t) ...)= guard for the submenu. Two function
variables (=org-scribe-planner-wordcount-function=,
=org-scribe-planner-project-root-function=) already exist as indirection
points. Verdict: *severable by design* — the planner would run standalone
today with no changes.

** org-scribe → planner (the lighter direction)
- =org-scribe.el:102-104= adds =planning/= to =load-path= and loads the
  autoloads file.
- =ui/org-scribe-hydra.el:198-202=: the =W= key does a hard
  =(require 'org-scribe-planner)= — the only place that would *error* if
  the directory were absent.
- =reporting/org-scribe-health.el:255=: the plan section is already guarded
  by =(featurep 'org-scribe-planner)= — safe either way.
- Templates ship a =plan.org= placeholder; =org-scribe-project-structure=
  exposes =:plan-file=. Both harmless without the planner.
- *Tests*: ten =test-planner-*= files run inside org-scribe's suite;
  =test-planner-hooks.el= (798 lines, the largest test file in the repo)
  tests the *integration itself* and requires both sides loaded together.

** What the autoloads file actually does at startup
=planning/org-scribe-planner-autoloads.el= (95 lines) contains *only*
=autoload= forms — no hooks, no advice, no timers. Consequence worth
stating plainly: *until the user explicitly invokes a planner command*
(=F8 F8 W=, =M-x org-scribe-plan=, any dashboard), org-scribe behaves
byte-for-byte as if the planner did not exist. Even the "auto-load plan on
entering a project" hook is only installed when the planner itself first
loads, because the =add-hook= sits inside the =with-eval-after-load= block.
The planner is already lazier than CLAUDE.md's description implies.

* 3. The options

** Option A — status quo: bundled, lazy, always offered
What exists today. Zero startup cost, but two soft "leaks" toward users who
don't want a planner: the create-project flow *prompts* to create a plan
(=offer-plan-on-create=, default =t=), and every project template ships a
=plan.org= placeholder.

** Option B — re-separate into the standalone package
Move =planning/= (and its ten test files) back to the
=org-scribe-planner= repo; org-scribe drops the autoloads loading and
guards the hydra =W= key.

** Option C — bundled, with a per-project gate (recommended)
Keep the monorepo and the lazy loading, but make "does this project use the
planner?" an explicit per-project fact recorded in =.org-scribe-project= —
which is what "optional module we can add to a project" literally asks for.
Design in §6.

* 4. Why Option B loses (for this codebase, with one maintainer)

1. *The bridge problem returns.* Integration code — the hooks, the
   word-count push, plan auto-discovery, the health-report section, the
   hydra submenu — must live somewhere. With two packages the choices are:
   a third bridge package (the failed =integration/= shim pattern), or
   soft-references from each side to the other (the "circular dependency"
   the standalone repo already had to fix once). With one package, the
   integration section at the bottom of =org-scribe-planner.el= is simply
   *code*, tested by =test-planner-hooks.el= in the same suite. This is the
   single strongest argument, and it is historical fact, not speculation.
2. *Version skew becomes a compatibility matrix.* The integration works by
   advising named org-scribe functions and reading =.org-scribe-project=.
   Rename =org-scribe-ews-org-count-words= (which fable-plan.org §6
   explicitly recommends touching) and a separately-versioned planner
   breaks silently until updated in lockstep. In a monorepo that rename is
   one commit and the test suite catches everything.
3. *The maintenance evidence is already in.* One maintainer, two repos:
   the standalone copy went stale within months and is now 1,058 diff
   lines behind, missing known bug fixes (the DST schedule bug). Splitting
   again re-creates the exact situation that just demonstrably failed.
4. *Nobody consumes the package boundary.* Package separation pays when
   users install subsets or third parties depend on the pieces. Answer 1
   in fable-plan.org §8: this is a personal tool. The boundary would have
   an audience of zero.
5. *It would freeze the wrong API.* fable-plan.org §8 schedules structural
   surgery on precisely the planner/org-scribe seam: single progress
   ledger, deleting the =SYNC_DATE=/=SYNC_WORDS= model, replacing the
   =read-string=-rebinding advice with explicit arguments, cutting ~1,800
   lines of dashboards. A package boundary is a commitment to an
   interface; committing to *this* interface immediately before
   restructuring it is the worst possible ordering. If separation ever
   happens, it should be *after* the slimming, when the planner is small
   and its interface is the one worth keeping.
6. *The runtime benefits of separation already exist.* Startup cost: none
   (autoloads only, §2). Behavior when unused: none. Disk: ~5,200 lines of
   Elisp, irrelevant. The only user-visible difference Option B adds is
   that the code is harder to keep working.

The honest counter-arguments: a split enforces interface discipline (but
the fn-var indirection points already exist), and a standalone planner
could serve non-org-scribe Org users (but none exist, and the bundled file
still loads fine without org-scribe — bundling does not remove that
ability).

* 5. What Option B would actually cost (if chosen anyway)

For completeness, the checklist: reconcile 1,058 lines of drift into the
standalone repo (or force-overwrite it); move ten test files and give
=test-planner-hooks.el= a home that can load both packages; re-create a
degradation path for the hydra =W= key and the health section; document a
two-repo release procedure; keep both =load-path= stories working for your
init. Estimated effort: a solid day of careful work, recurring cost on
every seam-touching change thereafter — purchasing nothing that §6 doesn't
deliver in an hour.

* 6. Recommended design: the per-project gate (Option C)

The phrase in the request — "optional module we can *add to a project*" —
names the real requirement: some projects are planned, some are not, and an
unplanned project should never mention the planner. A packaging split
doesn't deliver that (an installed package still offers itself to every
project); a per-project switch does. Sketch, in increasing order of effort:

1. *Record the choice in the marker file.* The planner already reads and
   writes =.org-scribe-project= (=# Plan: <path>=). Add one line:
   =# Planner: yes/no=. =org-scribe-planner--offer-plan-on-create= writes
   =no= when the user declines, and every integration entry point
   (auto-load, mode-line, offer-on-create, health section) checks it
   first. Result: decline once, never asked or shown again *in that
   project*; other projects unaffected.
2. *Guard the hydra key.* Change =F8 F8 W= to check the gate: in a
   =Planner: no= project, either hide the entry or make it re-offer
   ("Enable the planner for this project?") — one =lambda= edit in
   =ui/org-scribe-hydra.el:198=.
3. *Stop shipping =plan.org= in every template.* Remove the placeholder
   from the four templates; let =offer-plan-on-create= (or =F8 F8 W p=)
   create it on demand. A fresh project then contains planner artifacts
   *only* if the writer said yes — the cleanest expression of "add to a
   project".
4. (Optional polish) A pair of commands,
   =org-scribe-planner-enable-for-project= /
   =…-disable-for-project=, that just toggle the marker line, so the
   choice is revisitable without editing the marker file by hand.

Total estimated effort: an hour or two plus tests, all inside the existing
test harness. This delivers everything the packaging split promises to the
actual user (you), with none of §4's costs.

* 7. What to do with the standalone repo

Archive it. It is five months stale, missing known bug fixes, and its
existence invites exactly the confusion this analysis had to untangle. Add
a final commit replacing the README body with a pointer: "Superseded —
org-scribe-planner is bundled with org-scribe since v0.5.0", then use
Codeberg's archive setting to make it read-only. (Deleting it would break
any old links; archiving preserves history and closes the door.)

* 8. Sequencing with the fable-plan.org action list

The per-project gate slots in cleanly as a new item between steps 3 and 4
of the revised top-five (fable-plan.org §8): it is small, independent of
the deletions, and makes the dashboard trial period more honest (the
planner only appears in projects where you opted in). The order becomes:

1. Delete tracktable bridge, compat file, integration shim.
2. Fix Commentary/README.
3. Slim relationships to a list.
4. *Per-project planner gate + archive the standalone repo* (this
   document, §6–§7).
5. Dashboard trial → cut to the three keepers.
6. Structural work: single ledger, advice → explicit arguments.

Re-evaluate packaging separation, if at all, only after step 6 — at that
point the planner will be roughly half its current size with a clean
call-based interface, and the split would be cheap. My expectation is that
once the gate exists, the motivation to split will have evaporated,
because the gate is what the split was standing in for.
