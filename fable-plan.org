#+TITLE: org-scribe — Product & Engineering Review
#+AUTHOR: Claude (Fable 5)
#+DATE: 2026-07-30
#+STARTUP: overview

Review of the =development= branch (v0.5.0, ~20,700 lines of Elisp: roughly
13,500 lines of source and 7,200 lines of tests across 25 ERT files).
Perspective: product fit for novelists + engineering sustainability. Companion
document: [[file:bugs-fable.org][bugs-fable.org]] (2026-07-29) covers concrete bugs; this one covers
product shape.

* 1. Summary of the software

** What it does
org-scribe is an Emacs package that turns Org-mode into a novel-writing
environment. It scaffolds a project from bilingual templates
(=org-scribe-templates/novel-{en,es}/=, =short-story-{en,es}/=), then layers on:
ID-based linking between scenes and characters/locations/plot threads
(=linking/=), metadata-aware word counting (=counting/=), org-ql searches over
scene properties (=search/=), four writing workspaces (=modes/=), project-aware
capture (=capture/=), a health report (=reporting/=), Spanish dictionary tools
(=language/=), a scene-break export filter (=export/=), a hydra menu (=ui/=),
and a large bundled writing planner with dashboards (=planning/=, ~5,200 lines
— a quarter of the entire codebase).

** Core product
The genuinely differentiated core is the *scene metadata system*: scenes carry
=:POV:=, =:CHARACTERS:=, =:LOCATION:=, =:PLOT:= properties holding stable
=[[id:...]]= links, and everything else (search, column view, health report,
plot timeline, tooltips) is built on top of that. This is a real idea that
plain Org does not give you, and the =org-scribe-define-entity= macro in
=linking/org-scribe-linking-core.el= is a clean way to express it.

** Target user
An Emacs-proficient novelist writing in Spanish and/or English — in practice,
the profile of the author. Evidence: the RAE dictionary and WordReference
synonym lookup are Spanish-only (=language/org-scribe-dictionary.el=; English
gets delegated to the optional =powerthesaurus=), templates and file detection
are bilingual (=novela.org= / =cuento.org=), and two of the "recommended"
dependencies are the author's own non-archive packages (=org-context-extended=,
=org-tracktable=). Nothing wrong with a personal tool, but the README pitches a
general "batteries-included toolkit," and several review points below hinge on
which of the two it is meant to be.

* 2. Current functionality

** Central features (implemented, tested, coherent)
- *Project scaffolding* — =templates/org-scribe-project.el=; novel and short
  story, EN/ES, variable substitution, git init, scene/chapter insertion.
- *Entity linking* — =linking/org-scribe-linking-core.el= macro plus
  character/location/plot modules; registry-driven =org-scribe-relink-project=
  in =org-scribe-link-update.el= is a good consolidation of what used to be
  per-entity commands.
- *Word counting* — =counting/org-scribe-wordcount.el=: per-heading
  =WORDCOUNT= properties, dblocks, optional count-on-save, ID-minting rules.
- *Search* — =search/org-scribe-search.el= (186 lines): six focused org-ql
  commands that handle both plain names and ID links. Small and exactly right.
- *Health report* — =reporting/org-scribe-health.el= (335 lines): progress,
  scene completion, missing properties, orphans, plan status in one buffer.
  This is the best "make the writer's life easier" feature in the package.
- *Hydra menu* — two-tier F8 F8 menu; the recent split into everyday verbs vs.
  upkeep submenu was the right instinct.
- *Writing workspaces* — =modes/org-scribe-modes.el=: write/focus/edit/navigate
  with save-restore of window state.

** Secondary features
- *Writing planner* (=planning/org-scribe-planner.el=, 2,822 lines) — plan
  struct, schedule generation, calendar buffer, milestones, recalculation,
  agenda sync, session notes, spare days, and nine integration hooks/advices
  into the rest of org-scribe.
- *Planner dashboards* (=planning/org-scribe-planner-dashboards.el=, 2,381
  lines) — see §4; this is the single largest source of bloat.
- *Character relationships* (=linking/org-scribe-character-relationships.el=,
  639 lines) — typed relationships (type/strength/sentiment), DOT/Graphviz
  graphs, ASCII trees, tables, dblocks.
- *Entity tooltips* (=linking/org-scribe-overlays.el=) — opt-in, well scoped.
- *Column-view cleanup*, *export scene-break filter*, *capture system*,
  *dictionary tools*, *org-tracktable bridge* (=counting/org-scribe-tracking.el=
  is a single-function shim).

** Unclear, incomplete, or disconnected
- *Advertised but nonexistent*: the Commentary of =org-scribe.el:37-40= still
  promises "Analysis tools (dialogue, tension, word frequency)", "Name
  generator and writing prompts", and "Export presets for various formats".
  None of these exist anywhere in the code (=tension-level= is merely a scene
  property name in =core/org-scribe-core.el:188=). The README makes similar
  claims ("translation support", "automatic language detection") that resolve
  to optional third-party packages with thin or no glue.
- *Dead weight kept alive*: =integration/org-scribe-planner-integration.el= is
  a zero-function no-op shim; =core/org-scribe-compat.el= carries the entire
  obsolete =org-scribe/= namespace. Both are pure maintenance surface for a
  package that (apparently) has few external users to protect.
- *Three overlapping progress-tracking systems*: (1) =WORDCOUNT= properties in
  the manuscript, (2) org-tracktable's daily table, (3) the planner's
  =DAILY_WORD_COUNTS= with its =SYNC_DATE=/=SYNC_WORDS= baseline model. They
  are bridged by advice and hooks rather than sharing one source of truth, and
  the recent commit history ("fixed bug with word counting", "fixed hook
  bugs", =wordcound_planner_integration.org= in the working tree) shows this
  seam is where the bugs live.
- *i18n that isn't*: =core/org-scribe-messages.el= (271 lines) routes every
  user-facing string through =org-scribe-msg= but is monolingual English by its
  own admission — indirection paid on every message with no current payoff.

* 3. Missing or weak functionality

** Missing capabilities a novelist would expect
- *A real export/compile story.* =export/org-scribe-export.el= only swaps
  scene-break markers per backend. There is no "compile manuscript" command:
  no export that excludes notes/properties/TODO states, no standard-manuscript
  ODT/DOCX preset, no front-matter handling, no per-chapter or partial export.
  For a tool that claims "from project creation to final export," this is the
  biggest hole — export is the moment a writer actually needs help fighting
  Org, and it is the least developed module (fewer than 100 effective lines).
- *Draft and revision workflow.* Projects get =git init= and a
  =revision.org.template=, but there is no snapshot/label-a-draft command, no
  compare-drafts view, no "mark scene as revised in draft 2" flow. Novelists
  live in revision; the package only supports drafting.
- *Timeline/chronology as a feature.* There is a timeline *capture template*
  (=org-scribe-capture-timeline=) and a plot-thread *presence* table, but no
  story-chronology support (scene dates, ordering vs. narrative order) — which
  the plot-timeline dblock name suggests but does not deliver.
- *Manuscript-level statistics that matter to writers*: chapter/scene length
  distribution, dialogue ratio, per-PoV word share. Ironically, the package
  computes fifteen kinds of analytics about the writer's *schedule* and almost
  none about the *text*.
- *Spelling/grammar/style guidance* — not even a pointer to flyspell/
  languagetool configuration in the writing workspaces.

** Underdeveloped existing features
- *English-language parity*: dictionary/synonyms are Spanish-only; the hydra
  binds =d= (RAE) and =y= (WordReference Spanish synonyms) unconditionally, so
  an English-only user gets two dead keys in the main menu.
- *Onboarding*: two "recommended" dependencies are personal Codeberg packages
  not on any archive. Accurate word counting — a headline feature — silently
  degrades without =org-context-extended=. =org-scribe-setup-check= mitigates
  this honestly, but the dependency itself is the problem (see §6).
- *The planner's plan file* is a bespoke Org serialization with its own
  escaping helpers, schedule-table parser, migration function, and
  buffer-erase safety layer (four dedicated test files). It works, but it is a
  hand-rolled database where a simpler model (a plain Org table the user owns,
  or reusing org-tracktable) would do.

* 4. Bloat, overengineering, unnecessary complexity

** The dashboards module is the headline problem
=planning/org-scribe-planner-dashboards.el= (2,381 lines) implements, for a
solo writer's daily word count: an ASCII burndown, a gnuplot burndown, a
gnuplot cumulative chart, an SVG progress dashboard with sparklines and
milestone badges, a velocity view, a velocity *trends* view, a velocity
*chart*, a multi-metric dashboard, a *split* dashboards view, a heatmap, a
performance-analytics view with day-of-week stats, a *consistency score*, a
*target-achievement rate*, an *efficiency ratio*, a *multi-window velocity*,
and a *momentum score* — plus =show-all-dashboards=. Three rendering backends
(ASCII/gnuplot/SVG) for the same data. This is a quantified-self product
grafted onto a writing tool, and it directly contradicts the stated goal of
avoiding "anything that distracts from writing." One progress view and one
trend view would serve; the rest is maintenance surface and menu noise.

** The planner core is an application inside the application
2,822 lines with its own date arithmetic (already bitten by the DST bug, H1 in
bugs-fable.org), schedule cache, calendar mode, milestone engine, two distinct
recalculation strategies, agenda sync, and session notes. Its integration with
org-scribe is done through the most fragile mechanisms Elisp offers:
- =:around= advice on =org-scribe-planner-new-plan= that intercepts
  =read-string= and =read-file-name= *by dynamically rebinding them* to
  pre-fill prompts (=org-scribe-planner.el:2651=), and a sibling that
  intercepts =--select-plan-file=;
- advice on =org-scribe-ews-org-count-words= to push counts;
- state persisted by rewriting the =.org-scribe-project= marker file;
- nine opt-out defcustoms that must be set *before first load* to take effect.
Each mechanism is individually clever; together they form a web where cause
and effect are far apart. The 798-line =tests/test-planner-hooks.el= — the
largest test file in the repo — is the tell: the integration itself is the
riskiest component.

** Duplicated progress tracking
As noted in §2: manuscript =WORDCOUNT= properties, org-tracktable, and planner
daily counts are three systems answering "how much did I write?" The
=SYNC_DATE=/=SYNC_WORDS= baseline model exists solely to reconcile #1 with #3.
Pick one ledger.

** Smaller items
- *Character relationships* (639 lines): typed strength/sentiment modeling,
  Graphviz export, ASCII trees, strength filters. Useful to some plotters, but
  it is the second-largest non-planner feature module and its five hydra
  bindings crowd the links menu. Candidate for "extras" status.
- *Message layer*: 271 lines of indirection for monolingual English (§2).
- *Compat + shim modules*: =core/org-scribe-compat.el= and =integration/…= are
  pure legacy surface; for a v0.5.0 package this history can simply be cut.
- *Commentary/README drift*: advertising nonexistent features (§2) is a
  product bug — it sets expectations the tool then fails.
- *Working-tree hygiene*: =#planner-integration.org#= autosave files and
  scratch notes (=tutorial_lisp.org=, =wordcound_planner_integration.org=) sit
  untracked in the repo root; they should be ignored or moved.
- The hydra main menu at ~30 bindings is at the edge of scannability; the
  two-tier reorganization helped, but every new feature has historically paid
  a key there (=W=, =H=, =R=, =L=, =T=, =C=…). The menu is the bloat gauge:
  when a feature needs a mnemonic like =6=, it is time to ask if it belongs.

** What is *not* bloat
Worth saying explicitly: the linking core macro, the messages-key discipline,
the module layout, =lexical-binding= everywhere, graceful degradation for
optional packages, and the 25-file test suite are all *good* engineering. The
problem is not code quality — bugs-fable.org shows real rigor — it is that
engineering effort has recently flowed to the periphery (planner, dashboards,
relationship graphs) rather than the core loop (write → tag → find → export).

* 5. Product alignment

** Does it make the writer's life easier?
The core loop does: create project, insert scene, tag it from completion
menus, count words, find scenes by PoV/character/plot, check health. That is a
genuinely better novel-writing environment than raw Org, and hard to get
elsewhere in Emacs.

** Is it focused?
No — it is two products sharing a repo. Product A is "Org-mode for
novelists" (linking, search, health, workspaces, counting): focused, aligned,
roughly 8,000 lines. Product B is "a writing-productivity analytics suite"
(planner + dashboards): 5,200 lines, three render backends, momentum scores.
Product B is where the recent bugs, the biggest test files, the advice-based
coupling, and the working-tree scratch notes all cluster. A writer opening
=F8 F8 W= to a planner with a dashboards *menu* containing a dozen views is
being invited to procrastinate with charts — the exact distraction the
product statement forbids.

** What to simplify, remove, postpone, reconsider
Condensed here; ranked concretely in §6. Reconsider the planner's scope
(keep goal + daily target + one progress view), collapse the three progress
ledgers into one, cut the compat/shim/i18n indirection, and redirect effort
to export and revision — the two things a novelist needs that are thinnest.

* 6. Prioritized recommendations

** Keep / strengthen
1. *Entity linking + health report + search* — the moat. Low effort, high
   value: extend health with text-level stats (per-PoV word share, chapter
   length spread) since all the data is already collected there.
2. *The two-tier hydra discipline* — adopt a hard rule: main menu only for
   actions used during a writing session; everything else behind submenus.
3. *Test suite* — keep; it is the reason refactors below are safe.

** Simplify / reduce
1. *[High impact, medium effort]* Collapse progress tracking to one ledger.
   Recommendation: make the planner's daily table the single source (it is the
   only one with targets), have the wordcount module write to it directly via
   a plain function call, and drop the advice on =org-scribe-ews-org-count-words=
   plus the =SYNC_DATE=/=SYNC_WORDS= reconciliation model. Retire the
   org-tracktable bridge or make it a documented alternative, not a parallel
   system.
2. *[High impact, medium effort]* Replace the =:around= advice that rebinds
   =read-string=/=read-file-name= with explicit optional arguments on
   =org-scribe-planner-new-plan= / =load-plan= (project-aware callers pass
   values; interactive callers prompt). Same behavior, debuggable call graph,
   and a large chunk of =test-planner-hooks.el= becomes unnecessary.
3. *[Medium impact, low effort]* Reduce dashboards to two views: one progress
   dashboard (current SVG-with-ASCII-fallback) and one history view (burndown
   or heatmap — pick one). Delete the remaining ~10 views and the gnuplot
   backend, or move them to a separate opt-in file that ships outside the
   default menu. Expected deletion: ~1,800 lines.
4. *[Low impact, low effort]* Fix the Commentary and README to describe only
   what exists; remove "dialogue/tension analysis", "name generator",
   "writing prompts", "export presets".
5. *[Low impact, low effort]* Gate the Spanish dictionary hydra keys on
   =org-scribe-project-language= (or availability), so English users don't
   carry dead menu entries.

** Remove / postpone
1. *[Remove, trivial]* =integration/org-scribe-planner-integration.el= (empty
   shim) and, at the next version bump, =core/org-scribe-compat.el=. A 0.x
   package with this few external users should not carry a deprecation layer.
2. *[Remove, low effort]* The monolingual message indirection — either commit
   to shipping Spanish messages (the author is the ideal person to do it, and
   the infrastructure exists) or inline the strings. Infrastructure without
   its feature is the worst of both.
3. *[Postpone]* Relationship strength/sentiment analytics and graph exports —
   keep add/view relationships; park the DOT/ASCII-tree/filtering machinery
   until a user asks for it.
4. *[Remove from repo]* Editor autosave files (=#…#=) and scratch notes in the
   root; add them to =.gitignore= or a =notes/= directory.

** Add / explore
1. *[Highest product value]* A real =org-scribe-export-manuscript= command:
   compile the novel to ODT/DOCX/PDF with notes, properties, and non-DONE
   scenes excluded, scene breaks applied, and a standard-manuscript preset.
   This closes the "creation to final export" promise and is worth more to a
   novelist than everything in the dashboards module combined.
2. *[High value, medium effort]* A minimal draft/revision workflow on top of
   the git init the templates already do: "snapshot draft N" (tag), "what
   changed since draft N" (word-count and scene-level diff in the health
   report), and a =REVISED_IN= scene property.
3. *[Medium value]* Publish =org-context-extended= (or vendor its counting
   function) so the headline word-count accuracy does not depend on a
   personal off-archive package.
4. *[Explore]* Story-chronology support (scene =WHEN= property + ordering
   report) — the timeline template implies it; the data model already fits.

* 7. Clarifying questions

1. *Audience*: Is org-scribe intended for public distribution (MELPA/NonGNU
   ELPA) or primarily as your personal toolkit that happens to be published?
   The answer flips several recommendations — the compat layer, the README
   claims, and English-language parity only matter for a public audience.
2. *Actual usage*: Which planner dashboards have you opened more than twice in
   real writing? Deleting the unused ones is the cheapest win in the repo, but
   only you know which those are.
3. *Progress ledger*: Do you actively use org-tracktable's table, or has the
   planner's daily tracking superseded it in practice?
4. *Relationships*: Have the strength/sentiment fields and Graphviz output
   been used on a real manuscript, or was one plain "A knows B" list enough?
5. *Export*: What is your current path from =novel.org= to something you'd
   send to a reader or editor? That workflow should drive the export module's
   design (recommendation Add-1).
6. *The two personal dependencies*: Are you open to vendoring the counting
   logic from =org-context-extended=, or is keeping it a separate package a
   deliberate choice?

* 8. Addendum — answers received and revised priorities (2026-07-30)

Author's answers: (1) personal tool for now; (2) dashboards untested — keep
all for now, reviewer to name 2–3 keepers; (3) the planner should supersede
org-tracktable; (4) a plain relationship list would be enough; (5) needs
clarification (see below); (6) separate packages are deliberate.

** Consequences for the recommendations

*** Upgraded to "do now"
- *Retire the org-tracktable bridge* (answer 3). Delete
  =counting/org-scribe-tracking.el= (a single-function shim), the hydra =r=
  ("track table") binding, and org-tracktable's entry in
  =org-scribe--dependencies= and the README. The planner's daily table
  becomes the single progress ledger alongside manuscript =WORDCOUNT=
  properties — two ledgers instead of three, and the door opens to removing
  the =SYNC_DATE=/=SYNC_WORDS= reconciliation model in a second step
  (Simplify-1 in §6 stands, now with a clear target state).
- *Delete the legacy layers* (answer 1). With no external users to protect,
  =core/org-scribe-compat.el= and =integration/org-scribe-planner-integration.el=
  can go immediately rather than "at the next version bump".
- *Slim character relationships to a list* (answer 4). Keep
  add/remove/view-as-list; park the type/strength/sentiment model, the DOT/
  Graphviz export, ASCII trees, strength filtering, and the graph dblock.
  This shrinks the 639-line module to its useful core and frees five of the
  nine bindings in the links hydra.

*** Downgraded or dropped
- *English-language parity, MELPA hygiene, README audience-proofing* — mostly
  moot for a personal tool. The Commentary/README fiction (features that
  don't exist) is still worth deleting for your own future orientation, but
  it is a five-minute cleanup, not a product issue.
- *Vendoring =org-context-extended=* (answer 6) — dropped; the separate
  package is deliberate. =org-scribe-setup-check= already covers discovery.
- *Message-layer i18n* — with a personal-tool audience, either outcome is
  fine; lowest priority of the simplifications.

** Dashboard keep-list (answer 2 — reviewer's pick)

Keep these three; they answer the only three questions a writing plan exists
to answer, with no overlap:

1. =org-scribe-planner-show-progress-dashboard= — "where am I today?"
   Today's target vs. actual, overall percentage, streak. The everyday view;
   keep the SVG variant with its ASCII fallback and drop the separate
   =…-svg= entry point (one command, best available rendering).
2. =org-scribe-planner-show-burndown= (ASCII path) — "will I finish on
   time?" The one chart that justifies having a plan at all. Keep the ASCII
   renderer as the single backend; the gnuplot variants add an external
   dependency to answer the same question.
3. =org-scribe-planner-show-heatmap= — "am I consistent?" A calendar heatmap
   is the highest-information-per-glance history view and replaces what
   org-tracktable was providing (answer 3 makes this more valuable, not
   less).

Deletion candidates once you've trialed them: velocity, velocity trends,
velocity chart, multi-metric, split dashboards, performance analytics
(consistency/momentum/efficiency scores), and the gnuplot cumulative chart —
each is a slower-to-read restatement of information the three keepers already
show. Suggested trial: use the planner for two or three writing weeks, note
which views you actually reopen, then cut the rest and the
=show-all-dashboards= aggregator.

** Question 5 — answered (2026-07-30)

The author uses the plain org-mode exporter and has not yet exported a
finished manuscript. Consequence: =org-scribe-export-manuscript= (Add-1 in
§6) is *postponed*, not designed speculatively. It moves from "highest
product value" to "build when the first draft nears completion" — at which
point the first real export session will produce the manual-cleanup
checklist (drawers, TODO keywords, notes headings, scene breaks, title page)
that becomes the command's specification. Until then, no export work; §3's
"missing export story" stands as a known, deliberate gap rather than a
priority.

** Planner packaging — decision (2026-07-30)

The question of splitting the planner back into the standalone
=org-scribe-planner= package was analyzed separately in
[[file:planner-optional.org][planner-optional.org]]. *Decision (author): Option C — keep the planner
bundled, add a per-project gate.* No package split; the standalone Codeberg
repo is to be archived with a pointer back to org-scribe.

The gate, summarized (full design: planner-optional.org §6):
1. A =# Planner: yes/no= line in =.org-scribe-project=, written when the
   user accepts or declines the plan offer, and checked by every planner
   integration entry point (auto-load, mode-line, offer-on-create, health
   section).
2. =F8 F8 W= guarded by the gate — in a =Planner: no= project it re-offers
   ("Enable the planner for this project?") instead of opening the submenu.
3. The =plan.org= placeholder removed from the four project templates, so
   planner artifacts appear only in projects that opted in.
4. Optional polish: =org-scribe-planner-enable-for-project= /
   =…-disable-for-project= commands to toggle the marker line.

Rationale in brief (evidence in planner-optional.org §1–§4): the standalone
repo is five months stale and 1,000+ diff lines behind; the two-package era
already produced a circular dependency and the now-dead =integration/=
shim; the autoloads-only bundling has zero startup cost, so a split buys no
runtime benefit; and a package boundary would freeze exactly the seam that
the structural work below is about to change. Re-evaluate separation, if at
all, only after step 6 below.

** Revised action list (now six steps)

1. Delete the tracktable bridge, compat file, and integration shim (small,
   zero-risk deletions; run the suite after).
2. Fix the =org-scribe.el= Commentary and README to describe reality.
3. Reduce relationships to add/remove/view-list; park the rest.
4. *Per-project planner gate* (decision above) + archive the standalone
   =org-scribe-planner= repo. Small, independent of the deletions, and it
   makes the dashboard trial honest — the planner only appears in projects
   that opted in.
5. After a 2–3-week trial, cut dashboards down to the three keepers above.
6. Then tackle the structural one: single progress ledger + replacing the
   =read-string=/=read-file-name= rebinding advice with explicit arguments
   (§6 Simplify-1 and Simplify-2), which becomes markedly easier once
   org-tracktable and the extra dashboards are gone.
