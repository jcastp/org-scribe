** DONE H1. DST transition duplicates a date in every planner schedule [verified]
CLOSED: [2026-07-29 mié 17:02]
:PROPERTIES:
:FILES: planning/org-scribe-planner.el:252,268,509-532,944-974
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:02]
:END:

All planner date arithmetic works by adding 86400-second increments to a
timestamp parsed at local midnight:

- =org-scribe-planner--parse-date= (line 252) does
  =(apply #'encode-time (parse-time-string "...00:00:00"))=
- =--generate-day-schedule= (509), =--generate-date-range= (944),
  =--get-day-of-week= (960) and =--add-days= (268) all iterate with
  =(time-add current (days-to-time 1))=.

Across the autumn DST transition (Europe: last Sunday of October), midnight +
24h lands at *23:00 of the same day*. Reproduced:

#+begin_example
day: 2026-10-24 00:00 CEST
day: 2026-10-25 00:00 CEST
day: 2026-10-25 23:00 CET    <- 2026-10-25 appears twice
day: 2026-10-26 23:00 CET
#+end_example

Consequences for any plan spanning late October:
- The schedule contains the transition date *twice*: duplicate calendar row,
  daily target counted twice in cumulative/expected totals, and the plan
  effectively loses its last day.
- =--get-day-of-week= misclassifies weekdays after the transition, so
  "Add: All weekends" marks the wrong days as spare.
- =--generate-date-range= produces a duplicated date in spare-day ranges.

The spring transition is survivable (00:00 + 24h = 01:00 next day) but leaves
all subsequent timestamps at 01:00, which is fragile.

*Fix*: do calendar-day arithmetic, not seconds arithmetic. E.g. parse dates at
noon, or compute with =calendar-gregorian-from-absolute= /
=(encode-time 0 0 12 d m y)=, or use decoded-time arithmetic
(=decoded-time-add= with =:day=).

** DONE H2. Accurate word counting silently disabled unless the user's init loads org-context-extended
CLOSED: [2026-07-29 mié 17:04]
:PROPERTIES:
:FILES: counting/org-scribe-wordcount.el:32-44
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:04]
:END:

=org-scribe-accurate-wordcount-p= is =(featurep 'org-context-extended)= — but
*nothing in org-scribe ever requires that library* (verified by grep; the only
reference is the =featurep= itself). =featurep= is true only after the feature
has been /loaded/, not when it is merely installed.

So for a user who has org-context-extended installed but whose init does not
explicitly =(require 'org-context-extended)= before counting:
- every count silently uses the plain =count-words= fallback, which *includes*
  property drawers, =:ID:= uuids, =WORDCOUNT= values, comments and metadata —
  inflated numbers get written into =WORDCOUNT= properties and pushed to the
  writing plan;
- =org-scribe--auto-wordcount-before-save= silently no-ops (line 163), so the
  save-triggered plan sync never runs at all.

Whether counts are accurate therefore depends on load order/luck, and the
degraded-mode warning is the only clue.

*Fix*: attempt =(require 'org-context-extended nil t)= inside
=org-scribe-accurate-wordcount-p= (memoized) or at module load.

** DONE H4. Daily auto-tracking drops all words written before the first count of a day
CLOSED: [2026-07-29 mié 17:09]
:PROPERTIES:
:FILES: planning/org-scribe-planner.el:2418-2461
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:09]
:END:

=org-scribe-planner--sync-daily-from-manuscript= rolls the per-day baseline
like this: on the first sync of a new calendar day it sets =SYNC_WORDS= to the
*current* manuscript total and records a delta of 0. Only words counted
*after* the day's first sync are ever credited.

Concrete failure: a writer using the natural "write, then hit F8 F8 a once at
the end of the session" workflow (or =org-scribe-auto-wordcount= with one save
per day) gets *0 words logged for every single day*, forever. The words are
not attributed to any day — they exist only in =CURRENT_WORDS=. This poisons
everything computed from =DAILY_WORD_COUNTS=: streaks, velocity, milestones,
heatmap, week totals, and both recalculation commands (which sum daily entries
as "cumulative-actual" and will conclude almost nothing has been written,
inflating the remaining daily target).

The tests (=test-planner-daily-sync-rolls-baseline-on-new-day=) codify this
behavior, so it is "intended", but it is intended in a way that loses data for
the once-a-day counter, and it makes the two progress models
(=CURRENT_WORDS= vs sum of dailies) permanently diverge.

*Fix*: when rolling to a new day, seed the baseline from the *previous* known
total (=org-scribe-plan-current-words= / yesterday's =SYNC_WORDS= + delta),
so delta = total − previous-total is credited to today.

** DONE H5. org-scribe-planner-today logs the whole manuscript total as one day's words
CLOSED: [2026-07-29 mié 17:12]
:PROPERTIES:
:FILES: planning/org-scribe-planner.el:1741-1777, 2549
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:12]
:END:

When org-scribe is loaded, =org-scribe-planner-wordcount-function= is wired to
=--wordcount-from-manuscript=, which returns the *cumulative* manuscript
total. =org-scribe-planner-today= uses that function's return value directly
as *today's* word count:

#+begin_src elisp
(word-count (or (and org-scribe-planner-wordcount-function
                     (funcall org-scribe-planner-wordcount-function)) ...))
...(list :words word-count ...)
#+end_src

With a 50,000-word manuscript, invoking =org-scribe-planner-today= writes a
daily entry of 50,000 words — corrupting every daily-based statistic and the
recalculation math. The prompt fallback ("word count for today") and the
integration semantics ("total words") disagree about what the number means.

*Fix*: in =-today=, compute today's delta from the sync baseline (or don't use
the cumulative function here at all and always prompt).

** DONE H6. Saving a plan destroys its Agenda Entries; syncing agenda duplicates them
CLOSED: [2026-07-29 mié 17:15]
:PROPERTIES:
:FILES: planning/org-scribe-planner.el:1092-1202 (save), 1539-1568 (agenda)
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:15]
:END:

Two interlocking problems:

1. =--save-plan= does =(erase-buffer)= and rewrites only the heading,
   properties and Schedule table. Any =** Agenda Entries= section previously
   created by =org-scribe-planner-sync-agenda= in the same file is silently
   deleted the next time the plan is saved — which happens automatically on
   *every word-count sync*. Agenda integration therefore cannot survive normal
   use.
2. =--add-agenda-entries= only checks that the heading exists; the schedule
   entries themselves are appended unconditionally at =point-max=. Running
   sync-agenda twice appends the full set of daily TODOs again — hundreds of
   duplicates.

Also =--update-agenda-file-list= calls =customize-save-variable=, rewriting
the user's custom-file as a side effect, and errors if =org-agenda-files= is
set to a string (file-of-files indirection) since =member= expects a list.

** DONE H7. DAILY_WORD_COUNTS round-trip corrupts entries whose note contains ":"
CLOSED: [2026-07-29 mié 17:19]
:PROPERTIES:
:FILES: planning/org-scribe-planner.el:1632-1653 (format), 1244-1266 (parse)
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:19]
:END:

The serialization format is =DATE:WORDS:NOTE:TARGET= and parsing splits on
=":"= taking fixed fields. A note like "fixed plot: rewrote scene 3" is
written verbatim, then parsed back as note = "fixed plot" with target =
=(string-to-number " rewrote scene 3")= = 0. Data silently mangled on every
load/save cycle. Similarly, a note containing "|" breaks the regenerated
Schedule table (and the table-notes parser that reads it back). The comma case
*is* handled cleverly (=--split-daily-counts-str= only splits before a date
pattern) but colons and pipes are not.

*Fix*: escape/strip =:= and =|= in notes on write, or use a robust encoding
(e.g. store the alist as a printed sexp in a drawer).

** DONE H8. Spare-day notes mutate into fake "0 words written" entries after one save/load cycle
CLOSED: [2026-07-29 mié 17:23]
:PROPERTIES:
:FILES: planning/org-scribe-planner.el:1655-1673, 1280-1296, 1176-1184
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:23]
:END:

=--add-spare-day-note= deliberately creates a *note-only* entry (no =:words=),
and =--counts-with-words= filters those out of the property. But the note
still appears in the regenerated Schedule table, and on the next
=--load-plan=, =--parse-schedule-table= merges it back as
=(:words 0 :note ... :target nil)= (line 1295). From then on the entry *has*
a numeric word count, so:

- in the calendar/save cumulative logic (=(if actual ...)=, lines 1177/1411),
  a note on any future or spare day is treated as "actual data" and *resets
  the Expected Total column* to the actual cumulative for all subsequent days;
- in =--compute-recalculation-data= (line 1883) the day no longer counts as a
  remaining working day (=(not (assoc date daily-counts))=), so adding notes
  to future days silently inflates the recalculated daily target.

** DONE H9. Word counting and plan sync respect narrowing — focus mode corrupts plan data
CLOSED: [2026-07-29 mié 17:53]
:PROPERTIES:
:FILES: counting/org-scribe-wordcount.el:57, planning/org-scribe-planner.el:2393-2399, modes/org-scribe-modes.el:187
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 17:53]
:END:

=org-scribe-ews-org-count-words= and the live-buffer branch of
=--sum-wordcounts= call =org-map-entries= without widening; =org-map-entries=
with nil scope honors the current restriction. org-scribe's own *focus mode*
narrows the manuscript to one subtree (=org-narrow-to-subtree=).

Sequence: enable focus mode → save (with =org-scribe-auto-wordcount= t) or run
a count → only the narrowed subtree's =WORDCOUNT= is refreshed, and
=--sum-wordcounts= sums the narrowed buffer → the "manuscript total" collapses
to one scene's count → the sync writes that tiny number to =CURRENT_WORDS= and
records a *large negative daily delta* in the plan. (Entity readers such as
=--get-all-entities= correctly use =org-with-wide-buffer= — these two paths
don't.)

*Fix*: wrap both in =org-with-wide-buffer= / =save-restriction= + =widen=.

** DONE H10. Short-story projects: entity system and templates disagree about heading levels
CLOSED: [2026-07-29 mié 18:06]
:PROPERTIES:
:FILES: linking/org-scribe-character-links.el:33-39, linking/org-scribe-location-links.el:30-36, linking/org-scribe-plot-links.el:34-40, org-scribe-templates/short-story-*/notes.org.template, capture/org-scribe-capture.el
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 18:06]
:END:

All three heading predicates require =(= (org-current-level) 1)=. But the
short-story template stores entities at *level 2* under section headings
("=** Protagonist: [Name]=" with =:TYPE:= under "=* Characters=", locations
under "=* Setting="). Verified in the shipped template. Consequences in
short-story projects:

- =org-scribe--get-all-characters= (and locations/plot getters) never find the
  template entities → set-PoV, set-characters, relationship commands, health
  orphan detection and searches all report "No characters found".
- Conversely, the *section headers themselves* match the name-based fallbacks:
  "=* Setting=" matches the location regexp, "=* Plot Threads=" matches
  "Thread". Once =org-scribe-relink-project= or the add-ids commands run, these
  section headers get IDs minted and become phantom entities offered in
  completion.
- Captured characters use a =(file ...)= target, so they are appended at
  level 1 at the end of notes.org — found by the predicate but outside the
  "=* Characters=" section, while plot-thread captures land at level 2 under
  "Plot Threads" and are therefore *invisible* to the plot getter.

*Fix*: make predicates project-type aware (accept level 2 under the right
section in short-story mode, exclude known section-header names), and use
=file+headline= targets for short-story captures.

** DONE M1. Default edit-notes regexp is wrong [verified]
CLOSED: [2026-07-29 mié 18:10]
:PROPERTIES:
:FILES: search/org-scribe-search.el:32-37
:END:
:LOGBOOK:
- State "DONE"       from              [2026-07-29 mié 18:10]

=org-scribe-edit-string= is the Lisp string ="\*EDIT\*\\|\*NOTE\*"= which
yields the regexp =*EDIT*\|*NOTE*=. =\*= in a Lisp string is just =*=, so the
trailing =*= quantifies the last letter: the regexp actually matches =*EDI=
followed by zero-or-more =T= s, and =*NOT= followed by zero-or-more =E= s.

same broken pattern. Intended value: ="\\*EDIT\\*\\|\\*NOTE\\*"=. (Also: this
=defcustom= lives in the search module, contrary to the "all defcustom in
core/org-scribe-config.el" convention.)

*Root cause found*: not leaked mutable state from an earlier test, but a
missing dependency. The advice that makes
=org-scribe-planner-load-plan= project-aware is installed inside
=(with-eval-after-load 'org-scribe ...)= in
=planning/org-scribe-planner.el=. The documented full-suite entry point

throughout). =test-planner-hooks-load-plan-skips-picker-in-project= is the

when run via the single-file recipe from CLAUDE.md

=test-load.el= requires =org-scribe=.

*Fix*: added a =test-hooks--with-load-plan-project-aware= helper macro in
=tests/test-planner-hooks.el= that installs the advice locally
(=advice-add=/=advice-remove= around the test body, skipping if already

three tests that exercise this advice's behavior

=load-plan-uses-picker-outside-project=,
=load-plan-uses-picker-when-no-plan-file=,
=load-plan-falls-through-for-placeholder=). This matches the file's own
stated design goal ("verifying that integration hooks ... work correctly
in isolation, without requiring org-scribe to be present") and makes the
test's result depend only on the behavior under test, not on which other
test files happened to load first. Verified stable across repeated runs of
the documented full-suite command (0 unexpected results, previously 1).

=test-planner-hooks-load-plan-skips-picker-in-project= fails in the full suite
run (=picker-called= is t) but *passes in isolation* — verified both ways. Some
earlier test leaves planner/org-scribe global state behind (current plan,
plan-path persisted into a marker file, advice, or the project-type cache).
Beyond the flaky test, this is a smell that the same globals can go stale in
real sessions (e.g. switching between two writing projects keeps the first
project's plan active silently — =--auto-load-plan= only runs when *no* plan
is loaded, so opening project B still shows project A's plan, mode-line and
syncs word counts into A's plan file).
